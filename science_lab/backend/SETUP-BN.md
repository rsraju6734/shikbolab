# ShikboLab — Supabase সেটআপ গাইড (Phase 9)

> ⚠️ **সৎ কথা:** এই ফোল্ডারের SQL আমি লোকাল PostgreSQL এ চালিয়ে পরীক্ষা করেছি, কিন্তু আসল Supabase এ এখনও চালানো হয়নি।
> তাই ShikboLab এখনও **ব্যাকএন্ডের সাথে সংযুক্ত নয়**। অ্যাডমিন প্যানেল ও শিক্ষার্থী লগইন এখনও ডেমো মোডে।
> সংযোগের কাজ (login ও data sync কোড) পরের ধাপ। এখন যা আছে তা হলো **ডাটাবেস নকশা + নিরাপত্তা নিয়ম**।

## কখন এটা করবে?
যখন সত্যিকারের স্কুলের কাছে বিক্রি করতে যাবে। তার আগে ডেমোতেই থাকো।

## ধাপ ১: Supabase প্রজেক্ট খোলো
1. https://supabase.com এ গিয়ে সাইন-আপ করো (ফ্রি প্ল্যানে শুরু করা যায়)।
2. **New project** চাপো → নাম দাও `shikbolab`, শক্ত Database Password দাও (**এটা কোথাও লিখে রেখো, কিন্তু GitHub/কোডে নয়**)।
3. Region: সবচেয়ে কাছেরটা (যেমন Singapore)।

## ধাপ ২: SQL চালাও (ক্রম মানতে হবে)
1. Supabase এ বাঁ পাশে **SQL Editor** খোলো।
2. `backend/01_schema.sql` এর পুরো লেখা কপি করে paste করো → **Run**।
3. তারপর `02_security.sql` → **Run**।
4. তারপর `03_functions.sql` → **Run**।
5. প্রতিবার নিচে "Success" দেখাবে। লাল error এলে স্ক্রিনশট দাও, আমি ঠিক করব।

## ধাপ ৩: প্রথম Super Admin বানাও
1. **Authentication → Users → Add user** এ নিজের ইমেইল ও **নতুন শক্ত পাসওয়ার্ড** দিয়ে ইউজার বানাও (এই পাসওয়ার্ড কোডে বসাবে না)।
2. SQL Editor এ এটা চালাও (ইমেইল বদলে নিজেরটা দাও):
```
update profiles set role = 'super_admin'
where id = (select id from auth.users where email = 'তোমার-ইমেইল@example.com');
```
3. এই এক কাজ ছাড়া কোথাও সুপার অ্যাডমিন বানানোর রাস্তা নেই। সাইন-আপ ফর্ম থেকে কেউ নিজেকে অ্যাডমিন বানাতে পারবে না।

## ধাপ ৪: প্ল্যান বসাও
`plans` টেবিলে তোমার প্ল্যানগুলো (student, family, school…) বসাতে হবে। প্ল্যান ম্যানেজার থেকে ঠিক করা তথ্য দেখে নিতে পারো।

## ধাপ ৫: কী কোথায় বসবে (সবচেয়ে গুরুত্বপূর্ণ)
| জিনিস | কোথায় | GitHub এ যাবে? |
|---|---|---|
| Project URL | `js/backend-config.js` | ✅ যাবে (পাবলিক) |
| **anon** public key | `js/backend-config.js` | ✅ যাবে (পাবলিক, RLS রক্ষা করে) |
| **service_role** key | কোথাও না (শুধু ভবিষ্যতে Edge Function এর secret) | ❌ কখনোই না |
| Database password | শুধু তোমার মাথায়/পাসওয়ার্ড ম্যানেজারে | ❌ কখনোই না |

`backend/config.example.js` কপি করে `js/backend-config.js` বানাবে। অ্যাডমিন প্যানেলের "সিকিউরিটি" পেজ service_role key বসালে লাল সতর্কতা দেখাবে।

## ধাপ ৬: নিরাপত্তা নিজে যাচাই করো
SQL Editor এ কোনো সাধারণ শিক্ষার্থী হয়ে পরীক্ষা করো (পরের ধাপে আমি টেস্ট স্ক্রিপ্ট দেব)। কী কী ঠেকানো হয়েছে, আমার লোকাল টেস্টে যা মিলেছে:
- শিক্ষার্থী নিজের `role` বদলে অ্যাডমিন হতে পারে না
- শিক্ষার্থী অন্যের প্রোফাইল, পেমেন্ট, সাবস্ক্রিপশন দেখতে পারে না
- শিক্ষার্থী নিজে `payments` এ সারি বসাতে বা নিজের অনুরোধ "approved" করতে পারে না
- শিক্ষক শুধু নিজের ক্লাস-রেঞ্জের শিক্ষার্থী দেখে
- অ্যাডমিনের `payments.manage` না থাকলে পেমেন্ট নিশ্চিত করা যায় না
- রোল বদলাতে পারে শুধু সুপার অ্যাডমিন, নিজের রোল নয়
- `audit_log` কেউ বদলাতে বা মুছতে পারে না

## যা এখনও বাকি (গোপন করছি না)
- **frontend ↔ Supabase সংযোগ কোড:** লগইন, অ্যাডমিন প্যানেল থেকে ডেটা পড়া/লেখা, শিক্ষার্থীর অগ্রগতি সিঙ্ক। এটা এখনও লেখা হয়নি।
- **আসল পেমেন্ট গেটওয়ে:** `payments.verified_by_provider` এখন সবসময় `false`। গেটওয়ে জুড়লে তার webhook (Edge Function, service_role দিয়ে সার্ভারে) এটা `true` করবে।
- **রেট লিমিট:** `events` টেবিলে যে কেউ লিখতে পারে। স্প্যাম ঠেকাতে Supabase বা Cloudflare এ আলাদা রেট-লিমিট লাগবে। SQL এ এটা হয় না।
- **ইমেইল ভেরিফিকেশন, পাসওয়ার্ড রিসেট, ডিভাইস লিমিট:** Supabase Auth এর সেটিংসে চালু করতে হবে।
- **ব্যাকআপ:** Supabase এর ফ্রি প্ল্যানে স্বয়ংক্রিয় ব্যাকআপ সীমিত। বিক্রির আগে পেইড প্ল্যান বা নিজের `pg_dump` রুটিন ঠিক করো।
- **content.js এখনও পাবলিক ফাইল:** লেসন/কুইজ কনটেন্ট GitHub এ থাকে (এটা ইচ্ছাকৃত, ব্যক্তিগত তথ্য নেই)। প্রিমিয়াম কনটেন্ট সার্ভার-সুরক্ষিত করতে হলে সেটা ডাটাবেসে নিতে হবে। এখন প্রিমিয়াম "তালা" শুধু ফ্রন্টএন্ডে।
